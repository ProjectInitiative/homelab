# Argo root-disk cache ring — activating keepers; warmup still suspended

Status: PR #317 merged and the live CSI ConfigMap reconciled. The Argo VM's launcher is absent (operator stopped it), and the TCP/13911 peer-only rules are active on all three capstans. This change requests one read-only root-PVC keeper per node; **do not run the full-disk warm Job until all three mounts, membership and a bounded peer read pass**. `argo-data` remains on the existing independent local cache; never join it to the root ring (different JuiceFS volumes must not share cache group membership). The DGX `dgx-model-cache` ring and capstan3's active model-cache Mount Pod remain untouched. **Pre-existing risk:** the model-cache PVC-wide image pin is arm64 while capstan3 is amd64; an unrelated future recreation of its currently running stock Mount Pod may fail. Protect the active capstan3 consumer and plan a separate, node-scoped correction before any rotation.

## Scope

- All three capstans are **amd64**. A native capstan2 in-cluster Kaniko Job built fork commit `6aaf22da` from a checksum-verified source archive and completed 1/1; registry HEAD verified `6aaf22da-amd64@sha256:97346b44ff1bf905a82fb12cc3cbc5e9ca907b1b2c190c28a79fe0c32e4b557c`. This is a registry artifact, **not** a tested capstan Mount Pod. Never use the DGX arm64 image.
- `clusters/mc.yaml` retains the generic Argo PVC mount patch and adds **node-specific `argo-root`** overrides after the capstan defaults. Each advertises its own `172.16.4.51/52/53:13911` and shares `cache-group=capstan-argo-root`; the existing cache directory `/mnt/jfs-cache/argo` and 100-GiB-per-mount limit are preserved. `argo-data` is unchanged. Dotfiles PR #16 landed as `80b4c71`, and runtime firewall inspection confirms bond0/TCP13911 allows the three capstan peer IPs on every host. A dev-node timeout is expected because the rule rejects non-peer source IPs. Actual peer traffic still needs a live-ring probe.
- `argo-root-ring-keepers.yaml` now requests **one replica per capstan** via GitOps so three root Mount Pods stay alive. Before this change, keepers were 0/0. Do not manually scale or delete Mount Pods to make the ring appear healthy.
- `argo-root-cache-warm.yaml` is a **suspended CronJob**. It cannot start on a schedule. An operator may later create one bounded Job from it after confirming the file exists, the three live ring members and the peer path. The Job mounts `argo-root` read-only on capstan2 and reads `/disk/disk.img` once, checks its 0–32GiB bound, and never writes guest data or evicts cache. This is a warm pass, **not a consistent backup** of a changing VM disk. No `argo-data` read is requested.

## Before activation

1. Confirm the amd64 registry image digest and build provenance, `argo-root` PVC/PV identity, `/disk/disk.img` name and actual size, free NVMe on each capstan, and the effective host firewall rules. Verify no incompatible listener occupies TCP/13911, then confirm actual three-way peer connectivity from the capstans once the keeper Mount Pods start. Do not inspect or print the JuiceFS metadata URL.
2. The operator stopped the VM before keeper activation. Keep it stopped while validating new root Mount Pods; do not manually delete any active Mount Pod or the VM PVC/PV. Preserve `/mnt/jfs-cache/argo` on every host. Restart the VM only after the ring and warmup are validated.
3. Confirm fresh Mount Pods report `6aaf22da-amd64` and ring flags, three *same-volume* members (UUIDs, advertised endpoints, heartbeat ages), and a bounded real remote NVMe peer read (owner counters and checksum; a healthy mount alone is not peer proof). Avoid a warm pass while membership is partial or changing: mount UUIDs reshuffle ownership on recreation.
4. Only after those gates, create **one** Job from the suspended CronJob. Read progress and exit status; verify per-owner cache growth, no peer errors, and VM guest responsiveness. No second/parallel whole-disk pass, `--evict`, `juicefs gc`, direct writes, or deletion of model-cache consumers. The stored disk image may be changing, so warmed blocks can be superseded; pre-existing local caches may also contain non-owner copies from before the ring. Do not claim snapshot consistency or exactly one physical copy until placement is independently measured.

## Rollback

If keeper activation fails, revert their replicas to zero through GitOps without touching `argo-data` or the VM disk. Before rotating mounts, revert only this Argo-root-only patch (and keepers at zero). After activation, quiesce the Argo VM via the operator's normal procedure before reverting the PVC-specific image/ring flags, then recreate **only** Argo root Mount Pods through normal CSI lifecycle. Preserve disk contents, old caches, PostgreSQL, Garage, and capstan3's model-cache Mount Pod. Do not use manual force-deletion as rollback.
