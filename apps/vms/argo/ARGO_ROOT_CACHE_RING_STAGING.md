# Argo root-disk cache ring — staged, not activated

Status: **draft only**. The Argo VM is live on capstan1. Do not merge this draft or rotate its active `argo-root` Mount Pod without an operator-approved VM maintenance/migration window. `argo-data` remains on the existing independent local cache; never join it to the root ring (different JuiceFS volumes must not share cache group membership). The DGX `dgx-model-cache` ring and capstan3's active model-cache Mount Pod remain untouched.

## Scope

- All three capstans are **amd64**. A native capstan2 in-cluster Kaniko Job built fork commit `6aaf22da` from a checksum-verified source archive and completed 1/1; registry HEAD verified `6aaf22da-amd64@sha256:97346b44ff1bf905a82fb12cc3cbc5e9ca907b1b2c190c28a79fe0c32e4b557c`. This is a registry artifact, **not** a tested capstan Mount Pod. Never use the DGX arm64 image.
- `clusters/mc.yaml` retains the generic Argo PVC mount patch and adds **node-specific `argo-root`** overrides after the capstan defaults. Each advertises its own `172.16.4.51/52/53:13911` and shares `cache-group=capstan-argo-root`; the existing cache directory `/mnt/jfs-cache/argo` and 100-GiB-per-mount limit are preserved. `argo-data` is unchanged. A port probe from the dev machine timed out for TCP/13911 on all three capstans; this does **not** establish whether capstan-to-capstan traffic is allowed. Qualify peer connectivity from the actual nodes before rollout.
- `argo-root-ring-keepers.yaml` has **zero replicas** for each node. Future operator rollout must keep one read-only root-PVC consumer on each node so three Mount Pods stay alive. GitOps may revert manual scaling; change desired replicas through the approved Argo workflow.
- `argo-root-cache-warm.yaml` is a **suspended CronJob**. It cannot start on a schedule. An operator may later create one bounded Job from it after confirming the file exists, the three live ring members and the peer path. The Job mounts `argo-root` read-only on capstan2 and reads `/disk/disk.img` once, checks its 0–32GiB bound, and never writes guest data or evicts cache. This is a warm pass, **not a consistent backup** of a changing VM disk. No `argo-data` read is requested.

## Before activation

1. Confirm the amd64 registry image digest and build provenance, `argo-root` PVC/PV identity, `/disk/disk.img` name and actual size, free NVMe on each capstan, and open cache-group TCP/13911 between the three **actual** capstan nodes. Ensure no incompatible listener occupies port 13911 and the CSI image can start on each node. Do not inspect or print the JuiceFS metadata URL.
2. Agree on a VM-safe cutover: current VM `virt-launcher` uses `argo-root` on capstan1; a ConfigMap change only affects **new** Mount Pods. Do not manually delete the active Mount Pod or the VM PVC/PV. Roll the VM through its authorized maintenance/migration workflow, verify existing `argo-data` behavior and guest health, then bring up the other two root-PVC keeper consumers. Preserve `/mnt/jfs-cache/argo` on every host.
3. Confirm fresh Mount Pods report `6aaf22da-amd64` and ring flags, three *same-volume* members (UUIDs, advertised endpoints, heartbeat ages), and a bounded real remote NVMe peer read (owner counters and checksum; a healthy mount alone is not peer proof). Avoid a warm pass while membership is partial or changing: mount UUIDs reshuffle ownership on recreation.
4. Only after those gates, create **one** Job from the suspended CronJob. Read progress and exit status; verify per-owner cache growth, no peer errors, and VM guest responsiveness. No second/parallel whole-disk pass, `--evict`, `juicefs gc`, direct writes, or deletion of model-cache consumers. The stored disk image may be changing, so warmed blocks can be superseded; pre-existing local caches may also contain non-owner copies from before the ring. Do not claim snapshot consistency or exactly one physical copy until placement is independently measured.

## Rollback

Before rotating mounts, revert only this Argo-root-only draft patch (and leave keepers at zero). After activation, quiesce the Argo VM via the operator's normal procedure before reverting the PVC-specific image/ring flags, then recreate **only** Argo root Mount Pods through normal CSI lifecycle. Preserve disk contents, old caches, PostgreSQL, Garage, and capstan3's model-cache Mount Pod. Do not use manual force-deletion as rollback.
